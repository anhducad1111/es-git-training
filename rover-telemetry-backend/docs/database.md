# Rover Telemetry Database Design

Source: `sql/schema.sql` (the implemented DDL). For more detail on the design rationale, see section "5. Database Design" of `rover-telemetry-frontend/docs/Central_Telemetry_Backend_Design_Proposal_v1.1.md`.

All tables use the `InnoDB` engine with `utf8mb4` encoding.

## ER Overview

```
rovers 1 ──< telemetry_readings   (linked by device_id; composite PK: device_id + recorded_at)
rovers 1 ──< telemetry_summaries  (composite PK: device_id + granularity + bucket_start)
rovers 1 ──< media_files          (linked by device_id)
validation_errors                  (holds device_uid but no foreign key — so bad data from an unregistered rover can still be recorded)
gateway_metrics                    (gateway-wide metrics, not tied to any rover)
sensor_limits                      (master settings table, keyed by field name)
firmware_releases                  (shared fleet-wide, not tied to any rover)
```

---

## `rovers` — Rover registration records

| Column | Type | Description |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | Internal ID |
| `device_uid` | VARCHAR(64) UNIQUE | Rover identifier (used as the API path parameter) |
| `name` | VARCHAR(100) NULL | Display name |
| `firmware_version` | VARCHAR(30) NULL | Current firmware version |
| `enabled_sensors` | SET(...) | Installed sensor types; defaults to all four |
| `last_seen_at` | DATETIME(3) NULL | Last time telemetry was received; used to derive status (ONLINE/DEGRADED/OFFLINE) in `GET /rovers` |
| `created_at` | DATETIME | Registration timestamp |

## `telemetry_readings` — Raw telemetry data (the most frequently written table)

| Column | Type | Description |
|---|---|---|
| `device_id` | BIGINT UNSIGNED | Foreign key to `rovers.id` (part of the composite PK) |
| `recorded_at` | DATETIME(3) | Server-stamped receipt time (part of the composite PK) |
| `temperature_c` | FLOAT NULL | Temperature |
| `humidity_pct` | FLOAT NULL | Humidity |
| `gas_ppm` | FLOAT NULL | Gas concentration |
| `distance_cm` | FLOAT NULL | Distance sensor reading |
| `auto_brake` | TINYINT(1) | Auto-brake engaged flag |

- **PK**: `(device_id, recorded_at)` — naturally clusters as a per-rover time series.
- **Index**: `ix_reading_brake (device_id, auto_brake, recorded_at)` — speeds up detecting `auto_brake` rising edges (obstacle-event extraction, used by `GET /events` and `summary`'s `obstacle_events`).
- Sensor value columns allow `NULL` because `enabled_sensors` can differ per rover (columns for sensors not installed stay `NULL`).

## `telemetry_summaries` — Precomputed statistical summaries (generated by `bin/aggregate.php`)

| Column | Type | Description |
|---|---|---|
| `device_id` | BIGINT UNSIGNED | Foreign key to `rovers.id` |
| `granularity` | ENUM('minute','hour','day') | Aggregation granularity |
| `bucket_start` | DATETIME | Start time of the aggregation bucket |
| `sample_count` | INT UNSIGNED | Number of samples in the bucket |
| `temp_min/avg/max`, `hum_min/avg/max`, `gas_min/avg/max`, `dist_min/avg/max` | FLOAT NULL | Per-sensor statistics |
| `obstacle_events` | INT UNSIGNED | Number of obstacle detections within the bucket |
| `computed_at` | DATETIME | When the aggregation ran |

- **PK**: `(device_id, granularity, bucket_start)`.
- Raw data is aggregated into this table every minute to speed up `GET /rovers/{uid}/summary` and `readings?resolution=minute|hour|day` (aggregating raw data on every request would be too slow, hence precomputation).

## `gateway_metrics` — Gateway (Pi 5) resource history

| Column | Type | Description |
|---|---|---|
| `sampled_at` | DATETIME PK | Sampling time (one row per minute) |
| `cpu_load_percent` | FLOAT | CPU load |
| `cpu_temperature_c` | FLOAT | CPU temperature |
| `memory_used_percent` | FLOAT | Memory usage |
| `disk_used_percent` | FLOAT | Disk usage |
| `ingest_rate_per_min` | INT UNSIGNED | Telemetry records received in the last minute |
| `database_size_mb` | FLOAT | Database size (MB) |

- Has no `device_id` column since these values describe the gateway as a whole, not any individual rover.
- Written every minute by `bin/aggregate.php` and read by `GET /api/v1/system/history`. Also the source data for the SYSTEM tab's database-size growth projection chart.

## `validation_errors` — Records of data rejected by validation

| Column | Type | Description |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | |
| `device_uid` | VARCHAR(64) NULL | Sender (no foreign key, since it may be an unregistered rover) |
| `received_at` | DATETIME(3) | Receipt time |
| `error_code` | VARCHAR(40) | e.g. `OUT_OF_RANGE`, `MISSING_FIELD` |
| `detail` | VARCHAR(255) | Error detail message |
| `raw_payload` | TEXT NULL | The raw received payload (for investigation) |

- The `ix_validation_time (received_at)` index speeds up period-based aggregation such as `GET /validation-errors/summary?window=24h`.
- Note that this table stores `device_uid` (a string) rather than `device_id`, and has no foreign key constraint. **This is a deliberate design choice so that invalid submissions from a rover that doesn't even exist can still be recorded.**

## `media_files` — Photo/video metadata

| Column | Type | Description |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | |
| `device_id` | BIGINT UNSIGNED | Foreign key to `rovers.id` |
| `media_type` | ENUM('photo','video') | Inferred automatically from MIME type |
| `file_path` | VARCHAR(255) | Storage path of the actual file (excluded from API responses — hides gateway filesystem details) |
| `captured_at` | DATETIME(3) | Capture/acquisition time |
| `file_size_bytes` | INT UNSIGNED | File size |
| `mime_type` | VARCHAR(50) | MIME type |
| `original_filename` | VARCHAR(200) NULL | Original filename |
| `file_hash` | CHAR(64) NULL | SHA-256 hash (computed server-side; used for tamper detection / dedup) |

- The `ix_media_device_time (device_id, captured_at)` index speeds up the GALLERY tab's per-rover, time-ordered listing.

## `sensor_limits` — Master settings for sensor validation ranges

| Column | Type | Description |
|---|---|---|
| `field` | VARCHAR(30) PK | Sensor field name (e.g. `temperature_c`) |
| `min_value` | FLOAT | Lower bound |
| `max_value` | FLOAT | Upper bound |
| `updated_at` | DATETIME ON UPDATE CURRENT_TIMESTAMP | Last updated |

Seed values (via `INSERT ... ON DUPLICATE KEY UPDATE` in `sql/schema.sql`):

| field | min | max |
|---|---|---|
| `temperature_c` | -40 | 85 |
| `humidity_pct` | 0 | 100 |
| `gas_ppm` | 0 | 10000 |
| `distance_cm` | 2 | 400 |

- Updates via `PUT /config/sensor-limits/{field}` **only affect validation of data received afterward — they are not retroactive** to existing `telemetry_readings`.

## `firmware_releases` — Firmware distribution metadata

| Column | Type | Description |
|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT PK | |
| `version` | VARCHAR(30) UNIQUE | Version string (must be unique) |
| `file_path` | VARCHAR(255) | Storage path of the actual file (excluded from API responses) |
| `file_size_bytes` | INT UNSIGNED | File size |
| `mime_type` | VARCHAR(50) | Defaults to `application/octet-stream` |
| `file_hash` | CHAR(64) NULL | SHA-256 hash |
| `release_notes` | TEXT NULL | Release notes |
| `created_at` | DATETIME | Upload timestamp |

- **Shared across the entire fleet**, not per-rover (no `device_id` column) — the design mirrors the upload/serve pattern used for `media_files`.

## Design Notes

- **Timestamp precision**: `telemetry_readings.recorded_at`, `rovers.last_seen_at`, and `media_files.captured_at` use millisecond precision (`DATETIME(3)`) to avoid collisions at the same second under high-frequency transmission.
- **Storage capacity and retention**: `bin/retention.php` thins out old raw data as a nightly batch job. See design spec sections "8.3 Storage growth on the Pi 5" and "8.4 Retention" for operational capacity estimates.
- **Storage path convention**: media/firmware files are stored under `MEDIA_STORAGE_PATH` / `FIRMWARE_STORAGE_PATH` (`storage/media` / `storage/firmware` in the dev environment), with the database holding only the path and metadata — binaries are never stored directly in the database.
